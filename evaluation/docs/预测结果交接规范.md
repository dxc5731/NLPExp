# 预测结果交接规范（第一阶段 v1.0）

> 进度补充（2026-10-17）：下文保留第一阶段建立时的范围描述。第二、三阶段已实现统一评分及轻量 run_info 核查；真实接入采用[接入指南](真实模型预测接入与评估指南.md)及 [机器字段模板](../configs/run_info.example.json)。预测 JSON 约定不变；自动核查不证明模型真实、无泄漏或可复现。

适用：课程 B 方向，IMCS-V2-NER / Task1 五类实体识别。2026-10-16 建立。本规范是本组的**工程交接约定**，不是老师指定的文件名或正式实验设计；不决定训练参数、模型选择和实验划分。当前仅实现输入校验，不计算任何效果指标。

## 1. 交付目录与预测 JSON

每种方法、每次运行单独建目录，避免覆盖历史记录。交给评估负责人的最小目录：

```text
<method>/<run_id>/
├── predictions_dev.json       # 当前阶段交接；必须对应完整平台 dev
├── predictions_test.json      # 后续完整平台 test 推理时交接
├── run_info.json
├── config/                    # 配置文件或 run_info 内完整内联配置
└── logs/                      # 实际训练（适用时）与推理日志
```

没有完成 test 时无需制造 `predictions_test.json`；两份预测分别写对应的运行记录，可使用不同子目录。不要把 dev 预测改名当作 test。将来若团队另定本地评估子集，必须另行记录 ID 清单及协议版本，不能悄悄少交本规范要求的完整 dev。

预测必须是 UTF-8（无 BOM）的严格 JSON，不带注释，不含重复 key。第一层原始对话 ID，第二层原始 `sentence_id`，值为 BIO 字符串：

```json
{
  "example_dialogue_001": {
    "01": "O O B-Symptom I-Symptom O",
    "07": "O O B-Drug I-Drug O"
  },
  "example_dialogue_unicode": {
    "3": "O O O O O O O"
  }
}
```

**上例完全人工构造，仅是接口示例，不是模型结果。** 配套原文依次为 `孩子发热。`、`请用药甲。`、`A 😀，𠀀é`；完整可执行文件在 [接口示例目录](../examples/interface_example/README.md)。真实交接必须替换为原始数据的全部 ID 和模型真实输出。JSON key 的顺序不影响校验，但不得改编号；`"01"` 与 `"1"` 不同，句子 ID 可以不连续。

唯一允许的标签共 11 种，大小写必须一致：

```text
O
B-Symptom I-Symptom
B-Drug I-Drug
B-Drug_Category I-Drug_Category
B-Medical_Examination I-Medical_Examination
B-Operation I-Operation
```

- 相邻标签只用**一个 ASCII 空格 U+0020** 分隔；不得有首尾空格、连续空格、制表符、换行、不换行空格等其他分隔符。字符串中的 JSON 转义按解码后的实际字符检查。
- 原文每一个字符对应一个标签，标点、原文空格、英文及特殊 Unicode 字符全部计入。按 Python 3 的 `len(sentence)` 数 Unicode 码点，不按 UTF-8 字节、UTF-16 代码单元或视觉字形数计数。组合字符不合并；不做 NFC/NFKC 等归一化。
- 不得清洗、去空格、替换标点、归一化、裁剪原文或漏掉长句后半部分。无实体句子也需输出原文长度的 O 序列。
- BERT／子词方法自行完成 tokenizer 输出到原始字符的映射。不得交 `[CLS]`、`[SEP]`、`[PAD]` 或子词位置的标签；滑窗、长句分段后必须完整还原原句坐标，并记录处理方法。
- 每句独立满足 BIO：`I-X` 前面只能紧接同句的 `B-X` 或 `I-X`。句首 `I-X`、`O → I-X`、`B-Y/I-Y → I-X`（X≠Y）一律拒绝；`B-X → B-X` 可以表示相邻实体。
- 同一划分必须覆盖全部原始对话和句子。不允许漏句、漏对话、多出记录、改 ID、重复 key；数量相同不能替代 ID 集合完全一致。
- 校验器只报告问题，**不会截断、补 O、改 BIO 或静默修复**。队友需在自己的预测生成／对齐代码中处理并重新导出，保留处理说明与真实日志。

## 2. 原始数据与作者格式之间的关系

原始 ZIP：`data/IMCS-V2-NER.zip`。固定 SHA-256：

```text
84e34d2417b839d9fbe5c5f391e44de2a9b01bd5f31d576b8feccc78c1dfbc67
```

| 文件（ZIP 的 IMCS-V2-NER/ 下） | 对话 | 句子 | 组织与用途 |
|---|---:|---:|---|
| `IMCS-V2_train.json` | 2472 | 98529 | 原始对话，句子有 BIO_label |
| `IMCS-V2_dev.json` | 833 | 33267 | 原始对话，句子有 BIO_label |
| `IMCS-V2_test.json` | 811 | 32935 | 原始对话，有文本，无 BIO_label |
| `IMCS-V2-NER_test.json` | 811 | 32935 | 原始 ID 的空字符串模板，无文本、无答案 |

其他文件是 `README.txt`、`mappings.json`、`example_pred.json`，以及 ZIP 目录条目。`example_pred.json` 是随包示例，不是本组模型成绩。

原始文件形状为 `data[对话ID]["dialogue"]` 句子数组，每条取 `sentence_id`、`sentence`，train/dev 另取 `BIO_label`；内部预测是 `predictions[对话ID][sentence_id] = 标签字符串`，不要把原始句子数组直接交作预测。句子里的 `speaker` 是独立字段，不得擅自把它拼到 `sentence` 前再计算长度。

实际对话字段为 `self_report`，部分历史网页示例写作 `self-report`，应以当前包为准。`mappings.json` 的 BIO 映射仅列 `PAD/O/B-Symptom/I-Symptom`，不能直接作为完整五类标签表；`PAD` 不在交接标签集合内。

train/dev 的其他字段包括 `diagnosis, explicit_info, implicit_info, report, self_report`；句子还包括 `dialogue_act, local_implicit_info, speaker, symptom_norm, symptom_type`。test 只提供 `dialogue, explicit_info, self_report`，句子只有 `sentence, sentence_id, speaker`。答案及派生标注不得用于生成预测，校验器读取 BIO 仅用于原数据结构核验。

作者 [Task1 说明副本](https://github.com/lemuria-wchen/imcs21-cblue/blob/8d512c6635029bf068712d62cf2428e65c5e4a58/task1/README.md) 规定相同的双层 ID → BIO 字符串结构；[官方格式检查器副本](前期核验/format_checker_IMCS_V2_NER.py) 使用 Python `len(text)` 对比标签数并列出这 11 种标签。本组在此基础上增加重复 key、完整 ID 集合、单空格和 BIO 转移检查；不能宣称这些额外限制全是平台原检查器已实现的功能。

## 3. run_info.json：运行与复现记录

与预测一同提交，采用 UTF-8 JSON。下面按真实运行要求区分字段。不能编造未知版本、种子和时间；缺失必填信息需补齐或明确作为待补交，不能声称已完成复现核查。路径默认相对 `run_info.json`，命令另注明工作目录。

| 级别 | 字段 | 填写要求 |
|---|---|---|
| 必填 | `schema_version, artifact_kind, run_id` | 当前 `1.0`；真实预测为 `model_prediction`；运行 ID 唯一 |
| 必填 | `method.name, method.kind, method_version` | 方法名；如 bert/crf/dictionary_rules；模型 checkpoint／规则或词典版本的可定位标识 |
| 必填 | `data.version, data.split, data.source_file, data.source_sha256, data.archive_sha256` | 平台版、train/dev/test、实际原始 JSON 文件或 ZIP 内路径、原始 JSON 字节 SHA-256、上述固定原包哈希；不要填重新序列化后的哈希 |
| 必填 | `code` | Git revision + dirty 状态；有未提交改动须保留补丁／快照及哈希；没有 Git 则提供可获取的源码快照路径及 SHA-256。仅有“最新版”不够 |
| 必填 | `config` | 配置版本、配置路径及哈希；也可内联完整实际配置。不在本协议中预设超参数 |
| 必填 | `preprocessing, alignment` | 明写“无”或实际处理；包括字符对齐、特殊 token、长句还原策略（适用时） |
| 必填 | `prediction.file, prediction.sha256` | 预测文件名及最终交接文件的字节哈希 |
| 必填 | `inference_command, inference_working_directory` | 实际可重跑的完整命令及工作目录，不包含密码／密钥 |
| 必填 | `device, environment` | CPU/GPU 型号、Python 与相关库实际版本；附依赖清单路径也可 |
| 必填 | `inference_elapsed_seconds, timing_scope` | 实测非负秒数；说明是否含模型加载、预处理和写盘、是否排除训练 |
| 条件必填 | `random_seeds` | 有训练或随机过程时记录 Python/NumPy/框架等实际种子；确定性规则可为 null，并用 `seed_applicability` 写明不适用原因 |
| 条件必填 | `training` | 有训练时记录允许训练数据及其哈希、训练命令、配置、日志路径、checkpoint 标识；训练集词典也须记录构建数据／命令／日志，禁止答案泄漏 |
| 条件必填 | tokenizer／分段与还原信息 | 子词或分段方法写入 `alignment` 或对应配置；版本及处理须可定位 |
| 可选 | 时间戳、硬件内存、checkpoint 下载地址、说明 | 有则实填；耗时、版本等必填内容不能用这些可选说明替代 |

完整人工 [run_info.json 示例](../examples/interface_example/run_info.json) 配套接口样例，标记 `artifact_kind=interface_example`。示例中的文本与预测哈希由实际文件计算，设备／推理耗时为 null，因为没有发生模型运行；这些 null **不是允许真实运行省略必填信息**。

保留训练／词典构建及推理日志、环境依赖、实际配置、代码与模型版本定位信息。无需把巨大权重随预测交给评估负责人；能通过 checkpoint 标识、可访问位置或重跑命令复现即可。不要在项目或课程包放数据原文、密钥或大权重。本阶段校验器**不自动审核 run_info 或证明模型无泄漏、可复现**，由评估负责人按此表核查。

## 4. 校验命令与报告

Python 3.10+，只用标准库，CPU 可运行，无需安装训练框架。以下命令在评估模块根目录（仓库中的 `evaluation/`）执行。

先验证人工接口示例：

```powershell
python -X utf8 src/validate_predictions.py --data examples/interface_example/data_dev.json --predictions examples/interface_example/predictions_dev.json --split dev --report logs/validation/interface_example_20261016.json
```

收到真实 dev 预测后的命令（将预测路径换为真实交付位置）：

```powershell
python -X utf8 src/validate_predictions.py --data data/IMCS-V2-NER.zip --predictions "<实际运行目录>/predictions_dev.json" --split dev --report "<实际运行目录>/validation_dev.json"
```

`--data` 也支持单个原始 JSON 文件、文件所在目录或其上层目录（含 `IMCS-V2-NER/`）；ZIP 原地只读，不解压。按 `--split` 查找 `IMCS-V2_<split>.json`；test 优先读取有文本的 `IMCS-V2_test.json`，不存在时才回退到空模板 `IMCS-V2-NER_test.json`。多个同名候选导致歧义时拒绝，不猜文件；显式传入已知文件名与 split 不一致时拒绝。任意自定义源文件名无法证明真实划分，仍需人工核对哈希和 run_info。

不需要预测文件的真实数据核查：

```powershell
python -X utf8 src/validate_predictions.py --data data/IMCS-V2-NER.zip --split train --audit-data --report logs/validation/data_audit_train_20261016.json
python -X utf8 src/validate_predictions.py --data data/IMCS-V2-NER.zip --split dev --audit-data --report logs/validation/data_audit_dev_20261016.json
python -X utf8 src/validate_predictions.py --data data/IMCS-V2-NER.zip --split test --audit-data --report logs/validation/data_audit_test_20261016.json
python -X utf8 -m unittest discover -s tests -v
```

控制台简报包含状态、规模、错误计数。JSON 报告记录输入路径与 SHA-256、数据字段与数量、预测覆盖数量、原始句子通过／失败／未完整检查数量、各项检查状态，以及错误代码统计和典型位置（ID、0 起始标签索引／JSON pointer）。不写医疗原文。默认最多保存 30 条错误样例、每种最多 3 条，仍统计全部错误；用 `--max-examples` 调整总上限。一个问题可能影响多项检查，因此错误事件总数不等于失败句子数。

| 总状态／退出码 | 含义 |
|---|---|
| `PASS` / 0 | 此模式要求的全部检查完成且通过；audit-data 的 PASS 只表示源数据核验 |
| `FAIL` / 1 | 存在读入、结构、ID、标签、BIO 或长度错误；继续收集可检查的问题 |
| `NOT_RUN` / 2 | 无已发现错误，但有必需检查无法完成；不能当成通过 |
| 参数或报告写出错误 / 2 | 未完成正常校验报告流程，控制台说明原因 |

单项检查也有 `PASS/FAIL/NOT_RUN`、数量与原因；不适用项（如 test 金标准标签校验）为 NOT_RUN，不影响该模式其他必需检查。只有空模板时，字符长度无法核验，必须保留 NOT_RUN；即便 ID 和 BIO 都合法也不返回 PASS。遇到其他错误则总状态 FAIL，缺失检查仍分别保留。JSON 解析失败时，依赖解析的检查不能执行；合法的 JSON `null` 则属于根类型错误。重复 key 不会被普通字典解析静默覆盖后放行。

报告不得写回输入文件或传入的数据目录内，以保护原始数据；会覆盖同路径的旧报告，需保留历史时使用新的运行目录或文件名。工具按给定源文件核对，不内置强制官方规模／哈希，这样才能测试人工小数据；真实交接需另核对本规范固定哈希和完整规模。

## 5. 与天池最终提交的区别

内部 dev/test 预测采用同一种双层 JSON 结构；天池只接受完整 test 的正式预测，最终文件名必须是 `IMCS-V2-NER_test.json`，放在提交 ZIP 根目录，不套中间文件夹。`run_info.json`、训练日志和模型权重不混入该 Task1 预测 ZIP。本阶段不转换、不打包、不上传；后续还需官方格式检查、ZIP 内路径核对及网页任务选择。平台动态条件上传前重新查证，见 [现有本地评估与天池提交说明](本地评估与天池提交说明.md)，不在此重复历史表单条件。

## 6. 可直接转发的队友检查清单

> 请每种方法每次运行单独交目录：完整 `predictions_dev.json` + `run_info.json` + 实际配置／日志；后续 test 用 `predictions_test.json`。固定平台 ZIP 版本及哈希，保留原始对话 ID 和 sentence_id（不可重新编号）。每个原字符一个标签，含空格／标点；子词和长句先还原到原句，不输出特殊 token。只用规定的 11 种标签、单个 ASCII 空格分隔、严格合法 BIO，不漏句不多句不重复 key。先运行统一校验并交 PASS 报告；缺字段／NOT_RUN 不能算交接完成。补齐真实版本、种子（适用时）、推理命令、设备及实测耗时，不编造信息；不用随包传巨大权重。人工接口示例不能充当模型结果。

## 7. 下一阶段的前置条件

本阶段建立输入契约与校验基础；可以继续开发独立统一评分程序并用人工样例验算。真实模型验收与正式方法比较仍需队友交付预测和完整元数据。下一阶段的实体提取、精确匹配、零分母、逐字符汇总口径及与作者计分器的一致性须单独实现和核验，本工具没有实现这些功能。

具体 BERT 版本、是否接 CRF、超参数、正式训练／调参／评估用途、参数对比及实验结论仍由小组决定；本规范不替代这些决定。团队须遵守 [课程要求核对](课程要求核对.md) 中的 AI 使用边界，由成员独立完成正式实验设计与结果分析。
