总分公式：

\[
\mathrm{score}=\frac{\sum_{j=1}^{19}s_j}{19}
\]

只提交 NER 且其 F1 百分数为 88 时，总分为 88/19 ≈ 4.6316；即使 NER 为 100，总分也只有 5.2632。总榜低并不表示 NER 能力差，也不保证一定排最后。

## 4. 平台需要提交什么

每个正式方案分别生成一个文件，文件名必须为：

`IMCS-V2-NER_test.json`

内容结构如下（示例为虚构，真实文件必须使用完整测试 ID）：

```json
{
  "dialogue_id": {
    "1": "O B-Symptom I-Symptom",
    "2": "O O O"
  }
}
```

- 第一层是对话 ID，第二层是 sentence_id，值为用单个空格连接的 BIO 标签字符串。
- 一个原始 `sentence` 字符对应一个标签；包括标点和原始空白。BERT 的子词需要映射回这个字符坐标。
- `speaker` 是独立字段。不能因为网页展示了“医生：”就给 sentence 额外加前缀并输出额外标签。
- 输出标签是 `O`，以及五类实体各自的 `B-`、`I-`，共 11 种。`PAD`、`[CLS]`、`[SEP]` 不得进入最终预测。
- 原始模板的全部 32,935 句都需要覆盖，无实体的句子输出相应长度的全 O；不能跳过。
- 使用 UTF-8，保留 ID 字符串，不更改原始句子或字符顺序。

将预测文件放在 ZIP 根层级：

```text
submission_bert.zip
└── IMCS-V2-NER_test.json
```

提交 ZIP 不能像下载 ZIP 那样再套 `IMCS-V2-NER/` 文件夹。只交 Task1 就只放这一份 JSON；无需上传数据、模型权重、训练代码或其他任务的零分文件。不同方法各自打包并注明模型名，保存本地预测和包的哈希以关联平台分数。

官方格式检查命令（从文件所在目录执行）：

```text
python -X utf8 format_checker_IMCS_V2_NER.py IMCS-V2-NER_test_raw.json IMCS-V2-NER_test.json IMCS-V2_test.json
```

`IMCS-V2-NER_test_raw.json` 是原始空模板的副本，`IMCS-V2_test.json` 提供原始句子。检查器用严格字符串比较检查文件名，直接把 `output/IMCS-V2-NER_test.json` 当作第二参数会失败；应切换工作目录或使用明确记录的适配。

平台“提交结果”页面需登录。填写组织、模型并上传 ZIP；说明称历史提交处返回总分和各项明细，错误可点模型查看。每天最多 5 次，失败也计次。FAQ 称次日上午 8 点更新榜单，此为官方说明，不是本次实测的服务时效保证。尚未验证用户账号的实际上传和出分链路。

## 5. NER 到底怎样评分

平台正文明确采用 **实体级 F1**。作者链接的 `eval_task1.py` 提供可检查的实体抽取和计分实现：每句把 BIO 还原为 `(实体类型, 起点, 终点)`，在同一句内匹配，随后累计全部句子的实体数量。

- TP：类型和起止边界都与金标准一致的预测实体数。
- FP：预测出来但没有精确匹配金标准的实体数。
- FN：金标准存在、却没被精确预测出来的实体数。

\[
P=TP/(TP+FP),\quad R=TP/(TP+FN),\quad F1=2TP/(2TP+FP+FN)
\]

没有预测实体时 P 按约定置 0；没有正确实体时 F1 为 0。先累计计数再算整体 F1，不是每句话算一次 F1 后取平均，也不是五类 F1 简单平均。

例如金标准是完整的“呼吸困难 / Symptom”，只抽到“困难”或类型错了，严格实体评分都不算正确。这个错配产生一个 FP 和一个 FN。词典方法不能只比较去重后的实体文字集合；同词在不同句子、不同位置出现都是不同实例。

平台配置公开了 `IMCS-V2-NER-P`、`IMCS-V2-NER-R`、`IMCS-V2-NER-F1` 三项，其中 F1 是榜单主指标。百分制 89.2108 对应本地 [0,1] 数值约 0.892108。

### 已证实的评估陷阱

**作者脚本的“token-level”打印标题有误导性。**它调用 `seqeval.metrics.precision_score/recall_score/f1_score`，这些函数按实体序列评估，并非逐字符标签分类。不能把这组结果直接作为课程的逐 token 指标。`class_info` 中键名 `acc` 实际计算的是实体 precision，也不能误称准确率。

**格式检查器不是评分器，也不是完整 BIO 合法性检查器。**本次用合成样例运行原官方检查代码，确认它检查 ID 覆盖、字符串、字符数和标签集合，但孤立 I 标签、额外记录可以通过。具体记录在 `evaluator-contract-probes.json`，没有进行平台提交。

**非法 BIO 的处理会影响分数。**本次抽取原作者解析函数作独立探针：`I-Symptom I-Symptom O` 被提取成零实体；`B-Symptom I-Drug I-Symptom O` 会得到跨越错类型 I 的 Symptom 区间。这不是建议采用的标准 BIO 行为，也不能据此假定线上完全一样。应记录非法转移比例，统一约定是否约束解码／如何修复，并保存原始输出；不要对各模型使用不一致的隐式修复。

正常合法 BIO 上可以对齐实体级精确匹配口径；对异常序列不能未经验证就假定自写函数、seqeval 默认模式、作者脚本和服务器完全等价。

## 7. 用户的评估职责与课程要求怎样对应

你的理解是正确的：每种方法分别与标准答案比较，再比较方法间的表现。你负责的是把比较做公平、清楚、可复核，不只是上传文件拿一个分数。

| 评估层 | 输入与金标准 | 应提供的证据 |
|---|---|---|
| 本地字符级 | 同一版本 dev、同一批句子、原始字符对齐 | 逐字符 P/R/F1，明确标签集合、是否含 O、平均方式、特殊符号处理 |
| 本地实体级 | 同一版本 dev 的 BIO 金标准 | 严格实体 micro-P/R/F1，五类分别 P/R/F1 与 support |
| 方法比较 | 词典、CRF、BERT 的独立预测 | 得分差、同一案例上的不同错误、推理成本，所有结果注明 split |
| 平台测试 | 完整官方 test 的预测 | 平台 P/R/F1、提交时间、模型配置、文件哈希与单项排序截图 |

字符级的一种清晰口径是：把 BIO 作为 11 类分类问题，报告完整混淆矩阵和各标签指标；汇总 P/R/F1 明确是否将 O 排除。若用不含 O 的 10 类 micro 汇总，仍需让真实 O→预测实体计入 FP、真实实体→预测 O 计入 FN，不能先删除所有 gold=O 位置后再算。可另列全部字符 accuracy；含所有类别的单标签 micro-F1 等于 accuracy，会被大量 O 主导。

这不是抽象担忧：本次核验 dev 共 441,339 字符，其中 O 有 369,500 个，比例 **83.7225%**。机械地全部预测 O，也能得到 83.7225% 字符准确率，但实体召回和实体 F1 都是 0。此数值是根据数据统计计算的退化情形，不是训练模型结果。

教师复现可以运行同一版本 dev 上的评估和既定模型推理；官方 test 的分数通过平台记录验证。如果公开答案缺失，就不能承诺教师不接触平台也能从 ZIP 算出官方测试 F1。数据获取说明、包哈希、固定依赖、评估命令和预期输出应一并交付。

训练／调参边界：平台 FAQ 明确禁止 dev 作为训练集，测试数据禁止人工标注；允许外部数据增强。词典只能从 train 的 BIO 实体得到；训练数据中的 `symptom_norm`、`symptom_type`、`local_implicit_info`、`dialogue_act` 等金标准字段不能被当作预测时的输入来泄漏答案。若利用上下文、说话人或自述，所有方案的可用输入应写清楚，比较才可解释。

如果用官方 dev 进行模型选择，在报告中如实叫“验证集”，不要把反复挑选后的分数包装成未见测试成绩。另一条可行路径是仅在官方 train 内划出内部调参集，保留官方 dev 作为本地独立评估集；此时必须明确其来源仍是官方 dev，而非官方 test。两条路径的具体选择与设置由团队确定。平台分数用于冻结版本后的外部验证，不能把频繁试榜当作无代价的调参方式。

课程仍要求至少一个参数比较、至少三类错误与实际例证、至少三个课程原理点及可复现材料。平台成绩不能代替逐 token 指标、错误分析或成本记录。可重点理解：字符与子词对齐、BIO 约束与实体边界、数据划分和评价协议。具体比较设置和结果解释应由团队根据课程规则独立确定，保留人工判断与真实日志。

比较榜单时，只有同一平台测试口径的结果可直接作数值参照。不能拿本地 dev 的 90 分与榜单 test 的 89 分宣称领先。即使平台分数更高，也只表示该测试指标更高；不同外部数据、预训练模型、训练预算未知时，不等于受控实验中方法更优。
